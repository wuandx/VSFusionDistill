# DECISIONS —— 会改变结论的口径，按时间追加，不删旧条目

D1 不把 VSFusionDistill 当证据来源（只读它的数据文件，不引用它的结论）。
D2 `candidate` ≠ 标签。阶梯：candidate → human-reviewed candidate → verified-by-experiment，任何一级都不是 UXO GT。
D3 结论分三档：站得住 / 站不住 / 未知。不把"未知"写成"大概不是"。
D4 卡片冻结后重渲必须走 `resign`；像素变了必须重判。
D5 图片高度逐录音读，不许硬编码 780。
D6 几何闸只能否决，不能认证。
D7 只凭声呐图像，"近场亮团"与"下部 1.85 m 带"都无法与跨录音反复出现的特征区分（presence 检验）。
D8 同 beam 窗的跨录音比对只能降级、不能定罪：beam 是体固连坐标，不同录音时刻不对应。
D9 相机 label 是 640×360 空间，×3 才是 1920×1080。相机只给身份与姿态，不给位置。
D10 **"框压在物体上"不能证明时间对**。相机持续 re-aim，目标始终落在画面同一处，因此错位数秒的图像上框仍会盖住目标。判定时间对不对，只能看背景视差或做内容比对。
D11 **发布的相机图与同号声呐帧不是同一时刻，偏差逐录音、且必须逐录音实测**。2026-11-12 的实测（`2023-09-21_105230`）：
- 内容比对（缩略图 NCC）：aris 200 → SD 116（0.9990）、aris 400 → SD 524（0.9987）、aris 600 → SD 929（0.9986）；aris 780 无可靠匹配（0.71），弃用。
- 斜率实测 ≈2.03；按标称（相机 29.97 fps ÷ 声呐 15 fps）应得 **1.998**。两者不等，说明斜率不能用标称帧率推，
  只能按内容拟合（40 条实测 a 在 2.00–2.11，中位 2.053，对应实际约 14.6 Hz；1 条 4.19 属漏帧录音）。
- 官方匹配表本身的映射是 `g(f) = gopro_idx + (f − aris_onset) × 2 = 2f − 128`（该录音 gopro_idx 16、aris_onset 72）。f=400 → 672。
- 发布图实测落在 SD 524，即 `672 − 148`；而 148 正是容器读出的 start_time 差（−4.938 s × 29.97）。三个独立来源对上了：导出脚本按 SD 算出的索引被套用到 FHD，而 FHD 起点早 148 帧。
- 结论：**发布图（以及画在它上面的 label）比同号声呐帧早约 4.94 秒**。
- 修法：相机帧应按 `g(f)` 从 `clips_sd` 取，不得使用 `gopro/*.jpg`，也不得用 `start_time` 差反推。
D12 相机证据在按 D11 重定时之前，不进入任何结论。

D15 **审阅台右栏默认显示"重定时 SD 帧"，发布图降级为一个带偏移量标签的备用视图。**
- 依据：`out/camera_retimed_index.csv`（40 条逐帧 `sd_simultaneous`），SD 帧由 `python -m tools.sd_frames --recording <rec>` 解到 `out/camera_sd/<rec>/<sd:04d>.jpg`。
- 面板两种模式：`SD 同时刻`（默认，服务端 `/api/camera_sd/<rec>/<sonar_frame>`）与 `发布图`（旧行为，`/api/camera/...`，按钮上直接写"早 N 帧"）。
- **标注框只存在于发布图上**（label 是画在那张图上的），所以在 SD 模式下框用**虚线琥珀色**画，标签前缀 `label@发布图`，并在下方写明"位置不对齐，不要当本帧的框"。这不是装饰：框与重定时帧之间隔着 offset 帧的运动。
- 验证（105230，sonar 400）：`published jpg ↔ SD 525 = 0.9992`、`↔ SD 673 = 0.8844`，判词 `published_matches_released_slot`；服务端 `X-SD-Frame: 673`。三条旗舰录音的 SD 帧已全部落地（105230 1172 帧 / 101840 1024 / 110229 761）。
- 未做的增强（下一轮）：用模板跟踪把框平移到同时刻帧上，只有这样框才能与 SD 画面同框使用。→ 已由 D16 完成。

D16 **框可以被搬到同时刻帧上，但只能当"你当时框的那块东西现在在这"，而且要过往返检验。**
- 做法（`tools/cam_track.py`）：label 在 `sd_released` 那一格是**正确**的（D11 已证明发布图落在那里），从那一格取 `PATCH=28` 的图块，沿缓存里实际存在的 SD 帧逐步做 NCC 搜索（`SEARCH=9`），走到 `sd_simultaneous`。
- **模板不刷新**。刷新版在五帧上给出 47–214 px 的往返误差（跟丢到水面纹理），同一批数据和固定锚点相比只有 1–5 px。这一条是实测出来的，不是偏好。
- **每一步都必须能回家**：正向走到终点后，取终点图块反向再走一遍，回不到出发点就判失败。阈值：`MIN_MEAN_NCC=0.80`、`MAX_ROUND_TRIP=6` 缓存像素、`MAX_SHIFT_FHD=200`。失败返回 `ok:false` + 原因，页面退回虚线框并写明原因，不给一个看起来合理的错框。
- 语义边界：这是**平移跟踪**，说的是"这块图块现在在这里"，不是物体轮廓、不是重标、更不是 GT。位移是图像坐标里的表观位移，含相机运动与物体自身运动两部分，未分离。
- 面板：`/api/camlabel_tracked/<rec>/<frame>`（服务端把结果缓存在 `out/camera_track/<rec>/<frame>.json`，冷启 ~2.8 s、命中 ~2 ms），成功画**实线绿框 + `tracked · <class>`**，失败画原虚线框并在 note 里写 `本帧跟踪未通过：<reason>`。
- 验证：105230 上 12 帧抽样 7 帧通过；`f400` 位移 `[2, 20]` FHD px、`ncc 0.959`、往返 `1.0 px`；页面实测两种状态都出现过（500 → tracked，632 → stale/round_trip_failed）。

## D17 标注形状按"弧"来，不按"斑"来（2026-11-12，用户确认）

**决定**：在这批录音上，弹体的声呐回波是一条细弧/细线（长几十行、宽 1–3 行），
不是紧凑亮斑。因此标注框的口径是「弧上可见亮段 + 1.6 倍外扩」，`engine/arc.py` 是这条口径的实现。

**为什么改**：此前 `engine/compact.py` 给的是 5×5 px 的整块候选，`engine/echo.py` 的时域中位背景
会把弧整条减掉（它相对声呐几乎不动）。用户先指出"你看的不对"（我用卡片 p0.5–p99.5 拉伸看，把弧看成了点），
再用"感觉框有点小"否定 1.3 倍外扩，最后"可以"确认 1.6 倍。依据是原始灰度全扇面，不是卡片。

**明确否决的口径**：按标称长度 0.58 m 框（194 行）。194 行里真正有回波的只有 40–90 行，
其余是噪声——拿它训练等于教模型框噪声。**这条写下来是为了下次不再讨论。**

**验证**：`engine/arc.py` 在 24 张已签字画押的框上 IoU 中位 1.000（最差 0.973）；
`tests/test_16_arc.py` 4 条把这些钉住（含"平帧必须返回 None""margin 是唯一放大来源"）。

**边界**：1.6 是标注约定，不是测量；弧的两端更淡的部分没有框进去，因为再降阈值会把噪声连进来。
`identity` 仍是 unresolved——"这条弧是弹体"是用户的口径确认，不是本线测出来的。

## D18 框到哪儿为止，用"脊线是否连续"判，不用"背景是否干净"（2026-11-12，用户纠正后改）

我先前的说法是"等以后背景更干净了再框淡的那头"。**这句是错的**：这是声呐，散斑噪声是成像机制的一部分，
不存在"更干净的背景"。任何"等噪声降下去"的标注规则都是永远不执行的规则。

改成可执行的判据——**同一条回波在相邻两列上最亮的行必须接得上**：

- 沿列向右/左走，取列内最亮行；若与上一列的最亮行跳变 **> 6 行**，判为"脊线断了"，停止延伸。
- 同时要求该列峰值 ≥ `med + 1.5σ`，否则同样停止。
- 允许 ≤2 列的短暂空隙，总延伸上限 80 束。

实测（`2023-09-21_101840 f349`，也就是我判"细长迹"的那条）：从 x=24 到 x=64，最亮行依次
147 → 152 → 154 → 161 → 167 → 172 → 174 → 182 → 186 → 194 → 209，是连贯的；**x=65 之后
最亮行跳到 148→159→200→154→137，跳变 30–60 行，接不上**。所以 x>65 那段不是同一条回波，
是背景纹理。框停在 65 是对的，理由从"噪声太高"换成"脊线断裂"。

代码：`engine/arc.py::_extend_ridge`（默认 `extend=False`；即使打开，在这批数据上最多只多延伸
1–10 束，105230 f106 是 40→30）。这条写下来的用途是：以后再遇到"框是不是小了"，用脊线连续性回答，
不要用"背景干净不干净"回答。

## D19 两套划分并存：manifest 的，和我们自己的录音级划分（2026-11-12，用户选 2）

`manifest-resolved.json` 的 `paired_role` 是**逐样本**给的，且只覆盖约 18%（726 条里 57 条有 role）。
按它导出，剩下 655 条只能进 `unassigned`，训练时用不上。用户决定：**另给一版录音级划分**，两版并存。

规矩（写在 `tools/export_visible.py::_recording_splits`，可复算）：

1. **一条录音整体只进一个 split**，任何一帧都不会同时出现在两侧。
2. 每个类别里，**接受样本数最接近该类 20% 的那条录音**进 `val`；同样接近时按 `md5(recording)` 定序。
   这样避免"val 只拿到一条 11 样本的录音、而 300 个迫击炮样本全在 train"。
3. 计数只用 `retained/revised`，不用 proposals 总数（否则 100 个 proposal 只收 11 个的录音会被当成大录音）。

| 目录 | split 来源 | 现状 |
|---|---|---|
| `out/sonar_visible_dataset` | manifest 的 `paired_role` | train 53 / val 4 / val_id 14 / unassigned 655 |
| `out/sonar_visible_dataset_recsplit` | **我方录音级划分** | train 575 / val 151，无 unassigned |

`provenance.json` 的 `split_source` 分别是 `manifest_paired_role` 与 `ours_recording_level`，并逐条记 `recording_split`。
**原始 manifest 一个字节都没改**；这份划分是"我方选择"，不是仓库事实，写报告时必须标注。

本期 val：`2023-09-20_175000`（炸弹 92）、`2023-09-21_103927`（迫击炮 45）、`2023-09-21_123500`（手榴弹 14）。
类别比例 train 265/51/259、val 92/14/45（炸弹 74/26、手榴弹 79/21、迫击炮 86/14）。

**`--force` 是重建不是合并**：早前一版 `--force` 只覆盖不清理，`val/` 残留了上一次 split 的文件，
val 里出现 192 个炸弹标签而不是 92 个——现在 `--force` 会先 `rmtree` 目标目录。
